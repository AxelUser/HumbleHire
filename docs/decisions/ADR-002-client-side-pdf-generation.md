# ADR-002: Build PDFs in the browser with pdfmake

- **Status**: Accepted
- **Date**: 2026-05-20
- **Feature**: export

---

A CV is exported by building the PDF bytes in the browser from the CV data with pdfmake, then handing the user a direct download. The browser print pipeline (a print stylesheet plus `window.print()`) is rejected. How the editor renders that PDF in its live preview is a separate decision, in [ADR-007](./ADR-007-pdf-js-preview.md).

## Why build the PDF instead of printing

**One-click download.** A print dialog adds friction to every export: pick a destination, confirm a filename, remember to turn off headers and footers. Job seekers export the same CV many times across an application cycle, so that cost repeats. A direct download removes it.

**Consistent output.** Browsers ship different print engines, and page breaks, default headers and footers, font embedding, and background handling each diverge in ways CSS cannot fully control. For a tool whose only output is the PDF, that variance is worth avoiding. Building the bytes in code gives the same file on every platform.

**Mobile works the same way.** Mobile print pipelines are partial: iOS Safari routes through AirPrint or Save to Files and ignores parts of the print stylesheet, and Android varies by browser. Generating the PDF in code uses one path that works wherever the app runs.

**The preview can be exact.** Because the preview renders the same generated bytes the user downloads (see [ADR-007](./ADR-007-pdf-js-preview.md)), it is the file itself, not an HTML approximation styled to resemble it.

ATS compatibility is preserved as long as construction uses real text primitives rather than rasterising the layout. That is a constraint on how the export is built, not a reason to prefer one path over the other.

## Consequences

- Export is one click, with no dialog and no per-export configuration.
- Each theme is implemented in the PDF rendering layer rather than as a stylesheet, so adding a theme is more work than dropping in CSS.
- pdfmake (~1 MB) is lazy-loaded when any export is triggered, from either the editor or the dashboard.
- Layout primitives in pdfmake are coarser than CSS, and some effects available in HTML are inconvenient or impossible. Debugging layout means opening the generated PDF; devtools do not see into it.
